# 交互与恢复验收场景

在功能设计、修复或审查时，按实际风险选择以下场景。使用受控测试环境与测试数据；不通过真实扣费、发奖或删除验证设计。仅制定方案时列出预期，实际执行后才记录通过。

| 场景 | 操作与条件 | 应观察到的结果 |
| --- | --- | --- |
| 用户连续执行普通操作。 | 用户操作一个对象后立即浏览、移动或编辑其他对象。后台任务尚未结束。 | 输入持续响应；无关操作可用；已接受的动作没有被悄悄丢弃。 |
| 用户在后台故障期间继续操作。 | 测试环境让一个同步、计算或恢复任务延迟、超时或失败。用户继续操作不依赖该结果的功能。 | 无关功能持续可用。内部故障不触发全局遮罩、全局输入禁用或强制退回入口。 |
| 用户执行采用本地缓存的普通业务。 | 用户连续修改对象，测试环境延迟云端保存。检查业务模块与既有同步模块的实际调用链。 | 业务立即更新当前缓存，通过已有变更接口标记变化；`dirty` 与版本由现有数据或同步机制维护。业务不直接调用上传或等待云回执，现有同步模块统一保存，后续操作使用更新后的状态。 |
| 用户连续操作已加载的数据。 | 用户在数据已加载后连续执行普通业务，同时让旧云端读取延迟返回。检查每次业务结束后的调用链。 | 业务使用当前缓存，不逐次拉取并整体重载持久化数据；旧回读不覆盖新动作。必要的初始化、身份切换与明确恢复仍遵守其加载合同。 |
| 用户在旧保存失败后继续操作。 | 用户完成动作 A 并触发保存，随后完成动作 B。分别让 A 的保存超时、明确失败和旧响应迟到。 | A、B 的当前业务状态都保留；不回填提交前快照、旧云端数据或旧字段值，不撤销 B。最新 `dirty` 交由既有同步队列处理，不另建业务补偿流程。 |
| 用户在保存成功前再次修改对象。 | 同步模块提交版本 N 后，用户产生版本 N+1，再收到 N 的成功回执。随后恢复正常保存。 | 回执只确认 N；N+1 的缓存与 `dirty` 保留，并由既有同步模块继续写入数据库。不能提前把 N+1 显示为已保存。 |
| 用户的目标字段在排队期间被替换。 | 用户提交字段值 A，排队合并改为发送值 B；另检查目标值未形成实际写入的路径。 | 共享任务成功不能确认 A 已提交。显示、次数与完成事件只依据本次目标字段的真实结果，保留仍有效的新修改。 |
| 用户提交字段时另一个字段发生变化。 | 用户提交字段 A，等待期间同一记录的字段 B 再次修改。分别让回执确认 A 和只确认 B。 | A 的业务只按其真实依赖判断。确认 A 不清除 B 的新修改；B 的成功不能冒认 A 成功，无关 B 变化也不否认已确认的 A。 |
| 用户停止等待仍在执行的保存。 | 调用者超时或离开页面，原物理请求仍在执行。分别使请求迟到成功、失败和排队后项取消。 | 无效界面等待结束；原操作的数据保护保持至实际终态，随后正确释放。后续有效操作可执行，不重复写入、不清除新修改，也不残留保护。 |
| 用户在云端版本冲突时保留本地修改。 | 用户已有未同步修改，测试环境拒绝过期写入并返回旧快照。同步模块随后读取当前权威版本并处理冲突。 | 旧快照不覆盖当前缓存，权威版本校验仍有效；最新修改在既有冲突规则下处理，未确认前保留待同步状态，成功后按实际提交版本确认。 |
| 用户打开列表或预览。 | 展示查询读取缺少可选字段的旧数据。刷新后触发自动保存，再执行独立业务操作。 | 展示读取不隐式修改业务数据；自动保存不把展示加工结果提交为权威业务变更。独立业务操作仍按权威状态校验和结算。 |
| 用户连续消耗同一资源。 | 用户快速提交两个依赖同一余额、材料或名额的动作。 | 本地业务按更新后的缓存校验和扣除；远端合同确需预留或排队时按真实可用量处理。不超额消费，不因普通云存档未完成冻结资源或扩大等待。 |
| 用户重复点击独立远端命令。 | 用户连点提交。测试环境丢弃响应，但服务端已完成处理。 | 程序确认原操作的结果；同一次意图只生效一次，不重复扣费或发奖。 |
| 用户在乱序处理期间继续编辑。 | 用户连续修改对象。分别让旧请求晚执行、旧响应晚到达。 | 写入端与界面均保留较新的有效状态；必要的顺序与冲突处理符合业务语义。 |
| 用户在任务中途离开页面。 | 用户关闭面板、切换场景或账号，随后收到旧任务结果。 | 不抢焦点或重开页面；旧结果不写入新账号或错误对象，不清除新会话的 `dirty`；持久任务仍由原拥有者跟踪。 |
| 用户取消正在处理的任务。 | 用户分别在提交前、提交中和已生效后取消。 | 取消文案与实际能力一致；未撤销的业务仍有真实状态，不能假报取消成功。 |
| 用户关闭仍在等待二次确认的输入页面。 | 用户提交输入后关闭原页面，分别保持关闭和立即重开，再确认旧对话框。 | 尚未发出的旧意图不产生业务写入；新页面不受影响。已经发出的请求仍按原操作确认，不能假报撤销。 |
| 用户在已接受操作完成前关闭页面。 | 用户发起需要结算或记录冷却的操作，关闭页面后让该操作成功，再重新进入。 | 业务结果与相应结算或冷却按原意图恰好完成一次；不能因页面关闭漏记，也不能把普通后台查询算作新的付费或限次意图。 |
| 用户在受限输入流程失败后离开。 | 用户进入正常成功前不显示取消的输入流程，让处理明确失败或变为待确认，再使用退出入口。 | 退出入口实际可用，取消回调按约定执行一次；输入与未决操作按各自拥有者保留，不重复提交。 |
| 用户在断网后重新进入。 | 用户已执行需要保存的操作，随后断网或退出。用户恢复连接并重新进入。 | 已承诺保存的操作可恢复；本地缓存及待同步状态由既有机制恢复并继续保存，独立远端命令的未知结果先确认。没有永久禁用、重复操作或数据回退。 |
| 用户主动撤销本地编辑。 | 用户在产品支持撤销的编辑流程中主动撤销一次修改，同时让较早的保存响应迟到。 | 撤销按产品语义产生当前状态及新版本，由统一同步模块保存；旧回执不撤销这次撤销，也不影响后续编辑。存储失败不能冒充用户撤销。 |
| 用户遇到持续故障。 | 测试环境让服务长期不可用或始终拒绝请求。用户继续操作其他功能。 | 自动重试有边界；状态有可执行出口；无关功能可用；资源与任务不会无限积压。 |
| 用户在数据量较大时操作界面。 | 代表性低性能设备执行大量计算、加载、序列化或刷新。用户同时输入、滚动和播放动画。 | 输入延迟、长帧、内存和积压符合已约定预算；后台处理没有占满交互所需资源。 |
| 用户等待确实依赖结果的步骤。 | 用户进入无法预取或解耦的处理步骤。分别模拟快速完成、缓慢完成和失败。 | 快速完成不闪烁；慢任务有真实状态；只限制必要操作；失败后没有无穷读条。 |
| 用户在等待失败后恢复操作。 | 用户进入必要等待。测试环境分别触发超时、明确失败与结果未知，并超过自动恢复预算。用户使用界面提供的离开或恢复入口。 | 用户知道正在处理什么及下一步能做什么。无效读条结束，入口实际可用。未知操作仍可找回和确认，不重复提交，不盲目释放待确认资源。 |
| 用户结束设计规定的操作限制。 | 用户完成演出或回合，后台仍有收尾工作。测试环境同时模拟流程异常退出。 | 限制按设计条件及时解除；异常路径释放对应限制，后台收尾不延长全局锁定。 |

交付范围内出现非设计性全局阻塞、无解释或无出口的等待、永久待确认、无限读条、残留锁定、保存回滚或误清新修改时，记录为验收失败并阻止发布。修复后重跑触发路径及其恢复操作，同时核对最终业务结果；仅隐藏提示或直接解锁不能判定通过。

## 将原则应用到常见设计

- 编辑器自动保存：输入立即更新当前编辑缓存，通过已有变更接口记录变化；现有数据或同步机制维护版本，统一同步模块按版本合并保存。远端响应不覆盖更新的输入；只有对应版本满足持久化条件才显示“已保存”，失败时保留最新草稿与待同步状态，不恢复旧稿。
- 采用本地状态与云存档的游戏对象升级：通过本地校验后立即扣除当前缓存中的材料、更新对象，并通过已有变更接口标记变化。普通业务不主动上传或等待保存，后续动作使用最新缓存；统一同步模块失败重试时不还原材料或对象，不撤销后续玩家操作。
- 远端实时业务与独立云数据对象：按自身接口合同处理真实依赖与持久化。独立扣费命令丢失响应时确认原结果，必要的局部预留由原拥有者收尾；这些例外不改变普通缓存由统一模块保存的职责。
- 调试工具与临时存档：仅在明确的专用入口按其用途调用既有持久化接口；不能把调试或临时保存的做法复制到普通业务流程，也不能扩大真实数据写入权限。
- 搜索与预览计算：新输入使旧查询失效，后台计算受并发和内存预算约束；只接纳与当前输入匹配的结果，保留用户焦点。
- 场景或文件加载：优先预加载与渐进呈现；缺少必需资源确实无法进入时，显示实际处理事项与真实进度。失败时保留可恢复状态，并提供可用的返回或重试动作。

## 资源/前置不足的补齐验收

执行前检查现有同类功能的处理链，复用已有界面与入口。以下场景仅使用受控测试环境和测试资源；充值页只验证导航与退出，不真实支付，不使用真实扣费验证自动继续。

| 场景 | 操作与条件 | 应观察到的结果 |
| --- | --- | --- |
| 玩家刷新建筑交易所，贝壳不足。 | 玩家点击刷新，查看现有「缺少道具」弹窗中的获取途径，再进入钻石兑换并用测试资源补齐贝壳。 | 引导在几步内可完成。复用现有弹窗与兑换窗口，不新建界面。兑换后重新校验并自动刷新原交易所一次，不要求再次点击刷新。 |
| 玩家补齐资源，钻石不足。 | 玩家进入现有钻石兑换流程，测试余额不足，再关闭充值页。 | 打开现有充值页，不只显示不足 toast。测试不真实支付。关闭后玩家可继续操作，不残留遮罩或输入锁，原操作不误判成功。 |
| 玩家执行操作，多项道具不足。 | 玩家执行同时缺少多项道具或材料的操作，通过现有缺少道具弹窗查看并一次补齐全部缺项。 | 弹窗完整列出所有缺项及获取途径，允许一次补齐。补齐后重新校验，原意图仍有效时自动继续一次，不逐项反复触发不足提示。 |
| 玩家执行操作，前置条件不足。 | 玩家点击依赖尚未完成前置条件的操作，使用现有引导入口完成前置条件后返回。 | UI 明确引导玩家在几步内完成前置条件，复用现有入口，不新建界面。条件未满足前原操作不执行，不只改提示文案。 |
| 玩家补齐后执行原操作，资源仍不足。 | 玩家只补齐部分资源，或在继续前用测试操作消耗相关资源，再让原操作重新校验。 | 仍不足的原操作不扣资源、不成功，继续提供缺项与补齐入口。已确认的兑换按自身规则结算，不冒充原操作成功。 |
| 玩家退出补齐流程，或补齐失败。 | 玩家分别取消补齐、关闭原页面，并在测试环境模拟兑换失败或旧回调迟到。 | 无关操作持续可用，流程结束不残留遮罩或输入锁。已取消或失效的原意图不自动执行，不重复扣除资源或完成操作。 |

## 记录实际结果

每个执行过的场景记录执行者、动作、环境与数据规模、实际界面表现、最终业务状态和证据。性能场景使用实际测量值；未执行项写明缺口。不能仅凭没有报错、请求返回成功或静态关键词命中判定交互验收通过。
