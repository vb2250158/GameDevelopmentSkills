# 代码质量基线

本文件只规定项目没有更具体规则时的最低要求。语言、框架、团队格式化器、linter、类型检查器、目录结构和已有公开 API 约定优先；不要用本文件强迫所有项目采用同一种命名、异常、可空或异步写法。

## 先确认项目约定

实施或评审前检查目标范围内的格式化、静态检查和测试入口，例如 `.editorconfig`、formatter/linter 配置、编译器选项、测试配置、同目录的既有范式和 CI 脚本。已有自动规则时，按它们格式化并运行相关检查；不要自行扩大为全仓重排或顺手改造。

## 文件、类型和公开边界

- 一个文件的主要类型或功能应能从文件名看出；文件内辅助类型只服务该主功能。不要在无关功能之间塞“顺手通用”的工具。
- 类型、函数、变量和参数名称表达业务含义、单位、集合性或布尔判断，不使用无意义缩写、误导性名称或与职责无关的历史名称。布尔值、谓词和条件分支应读得出成立条件；集合、单项、时间/数量和键/显示名要能区分。
- 公开方法、事件、命令和数据结构必须说清输入、结果、失败方式及副作用。能保持私有的成员不要扩大可见性；不要为了“方便调用”暴露可被任意修改的内部状态。
- 新增抽象只在消除真实重复、隔离不稳定依赖、收窄公开边界或改善测试时引入。不能用只有一次调用、没有业务名字的包装层代替直接清晰的调用。

## 函数和控制流

- 每个函数围绕一个可说明的动作或查询。函数同时做校验、状态变更、持久化、通知和 UI 操作时，优先保留一个业务编排入口，并把可独立理解的步骤抽为命名明确的私有方法或已有模块调用。
- 条件使用提前返回或清晰分支减少嵌套；不要为了压缩行数写难读的复合条件、三元链或依赖副作用的短路表达式。
- 不要让参数、全局状态、集合或传入对象在调用方难以发现的情况下被修改。必要的修改应通过名称、返回值、命令对象或 API 契约明确；查询方法不应悄悄写入业务状态。
- 删除无效分支、注释掉的旧实现、不可达代码、无意义的临时变量和已经失效的兼容路径。保留兼容路径时，写明触发条件、移除条件和正式入口。

## 数据、错误和异步

- 可空、缺失、失败、未加载和空集合是不同状态时，不能都用 `null`、`false` 或魔法返回值混在一起。使用项目已有的结果类型、错误码、异常或显式状态表达。
- 不吞掉异常、不只记录后继续假装成功，也不把预期业务失败当作无上下文的通用异常。错误信息包含对排障有用的操作和身份，不记录不必要的敏感数据。
- 异步操作、取消、超时和资源释放遵从项目已有模式。不能启动未观察的后台任务；状态变更在成功、失败和取消后都要保持一致。
- 需要跨处复用的字面量仍遵守设计 Skill 的唯一入口规则；只在单一局部且无需解释时保留字面量。

## 新旧逻辑、归档和兼容

- V2 替代 V1 时，先找 V1 的调用点、注册、导出、配置、资源、文档和测试。旧格式仍可能进入系统时，只保留最小兼容层。用 `Obsolete`、`@deprecated` 或项目约定的紧邻注释明确已过时、替代入口、触发版本/条件、删除条件和最晚删除版本。兼容层只把旧输入迁移、转换或转发到 V2，不能继续维护一套 V1 业务规则。
- 不存在运行时兼容需要时，先确认 V1 所在文件或目录是否实际纳入 Git、SVN 或项目实际使用的版本控制，并且历史可以读取。目标文件/目录已跟踪且可追溯时，直接删除 V1；版本控制负责保存可恢复的历史，禁止为此再创建 `archive/` 副本。仅有仓库目录但目标文件被忽略、未跟踪、位于忽略目录或不在仓库范围内，不算已纳入版本控制。
- 只有 V1 文件没有可用的版本控制历史，且 V1 已确认无 bug、可正常运行、并且作为完整旧版本有保留价值时，才归档。把原文件移动到项目根目录 `archive/`，按原文件相对项目根目录的路径完整镜像，不复制第二份。例如 `Assets/Test.txt` 必须归档到 `archive/Assets/Test.txt`；文件名和扩展名保持不变。归档目录必须不参与编译、资源打包、代码生成、自动发现和正式入口索引；归档说明写明原路径、替代版本、归档原因和恢复方式。
- V1 有 bug、无法确认正常运行、只是临时代码、重复逻辑或没有保留价值时，直接删除，不归档。
- 过时标记不等于把整段旧代码注释掉。注释掉的实现不能参与编译和测试，也容易在后续被复制回正式路径；需要保留时归档，需要继续运行时用受控兼容层。
- 新旧逻辑切换在同一次改动中清理 V1 的调用点、注册、导出、配置键、资源引用、文档入口和只服务 V1 的测试。用搜索和最小构建/测试确认正式路径只剩 V2。
- 不留下没有去向的 `Old`、`New2`、`Backup`、`Temp`、`Legacy` 文件、永久关闭的 feature flag 或“以后可能用”的死逻辑。灰度和回滚使用项目既有发布或配置机制，并明确结束条件。

## 注释、日志和测试

- 注释解释原因、约束、非直观取舍或外部协议，不复述代码表面动作。过期注释比没有注释更糟，修改行为时同步更新或删除。
- 日志服务于可定位的事件、失败或诊断，不在高频路径无目的打印；记录足以关联问题的稳定标识，避免记录凭据、个人信息或完整敏感载荷。
- 新增或修改行为时，运行最小相关的格式化、静态检查、编译和测试。无法运行时，说明缺少的命令、依赖或环境，不把“未运行”写成通过。
- 测试验证可观察行为、边界条件和失败行为；不要只断言内部私有实现细节。修复缺陷时，优先补能复现该缺陷的测试，除非项目测试层确实无法覆盖。

## 改动自查

- 读者能否从名称、签名和调用点理解这段代码的目的、输入、输出和副作用？
- 同一失败或空值在不同分支是否得到一致处理？
- 是否只修改了本次功能或修复必需的范围，且没有掩盖无关格式化噪音？
- V2 是否已经接管全部正式入口；是否先检查了目标文件/目录的实际跟踪状态，并按兼容需要、版本历史、旧版本运行状态和保留价值决定删除或归档？
- 自动检查实际运行了哪些，哪些没有运行，原因是什么？
