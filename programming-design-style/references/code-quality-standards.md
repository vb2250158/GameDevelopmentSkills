# 代码质量基线

本文件只规定项目没有更具体规则时的最低要求。语言、框架、团队格式化器、linter、类型检查器、目录结构和已有公开 API 约定优先；不要用本文件强迫所有项目采用同一种命名、异常、可空或异步写法。

## 先确认项目约定

实施或评审前检查目标范围内的格式化、静态检查和测试入口，例如 `.editorconfig`、formatter/linter 配置、编译器选项、测试配置、同目录的既有范式和 CI 脚本。已有自动规则时，按它们格式化并运行相关检查；不要自行扩大为全仓重排或顺手改造。

## 文件、类型和公开边界

- 一个文件的主要类型或功能应能从文件名看出；文件内辅助类型只服务该主功能。不要在无关功能之间塞“顺手通用”的工具。
- 类型、函数、变量和参数名称表达业务含义、单位、集合性或布尔判断，不使用无意义缩写、误导性名称或与职责无关的历史名称。布尔值、谓词和条件分支应读得出成立条件；集合、单项、时间/数量和键/显示名要能区分。
- 公开方法、事件、命令和数据结构必须说清输入、结果、失败方式及副作用。能保持私有的成员不要扩大可见性；不要为了“方便调用”暴露可被任意修改的内部状态。
- 新增抽象只在消除真实重复、隔离不稳定依赖、收窄公开边界或改善测试时引入。不能用只有一次调用、没有业务名字的包装层代替直接清晰的调用。

## 函数和控制流

- 每个函数围绕一个可说明的动作或查询。函数同时做校验、状态变更、持久化、通知和 UI 操作时，优先保留一个业务编排入口，并把可独立理解的步骤抽为命名明确的私有方法或已有模块调用。
- 条件使用提前返回或清晰分支减少嵌套；不要为了压缩行数写难读的复合条件、三元链或依赖副作用的短路表达式。
- 不要让参数、全局状态、集合或传入对象在调用方难以发现的情况下被修改。必要的修改应通过名称、返回值、命令对象或 API 契约明确；查询方法不应悄悄写入业务状态。
- 删除无效分支、注释掉的旧实现、不可达代码、无意义的临时变量和已经失效的兼容路径。保留兼容路径时，写明触发条件、移除条件和正式入口。

## 数据、错误和异步

- 可空、缺失、失败、未加载和空集合是不同状态时，不能都用 `null`、`false` 或魔法返回值混在一起。使用项目已有的结果类型、错误码、异常或显式状态表达。
- 不吞掉异常、不只记录后继续假装成功，也不把预期业务失败当作无上下文的通用异常。错误信息包含对排障有用的操作和身份，不记录不必要的敏感数据。
- 异步操作、取消、超时和资源释放遵从项目已有模式。不能启动未观察的后台任务；状态变更在成功、失败和取消后都要保持一致。
- 跨处复用的符号值、可扩展内容和配置读取按 [数据驱动与数据归属](data-ownership-and-workflows.md) 判断，不在这里另维护一套字面量规则。

## 新增逻辑与校验边界

- **允许补充，先判断后果**：在已授权目标内，可以添加用户未逐项提出但确有必要的逻辑。说明它防止什么实际问题，并比较不添加、添加后误判及自身失败的后果；若防护会把轻微差异变成加载失败、数据丢失或整条链路不可用，应调整处理方式。不能把个人假设升级成业务硬约束，也不能以补充逻辑扩大权限或业务范围。
- **沿数据来源复用保证**：添加校验前，追踪数据生产、传输、解析和消费位置，确认已有校验覆盖的事实、适用身份/版本与有效期。可信上游已校验、到当前使用前数据及前提未改变的同一事实，直接复用结果或已有类型/接口保证，不再次遍历、解析、查询或请求。不能只凭“来自服务端”就认定已校验；也不为省掉小检查另造复杂认证或缓存框架。
- **只检查新增风险**：校验由能负责该约束的边界拥有。跨越不可信边界、发生数据变换、并发修改、账号切换或时效失效时，只重新检查受影响的约束。服务端鉴权、写入前的业务约束与原子提交不能由客户端早先检查代替；语义不同的检查不算重复。展示偏好、排列差异和非关键字段问题，除非有明确的正确性依赖，不应成为拒绝全部有效数据的条件。
- **最小范围失败，结果真实**：区分可恢复的单项问题与影响身份、金额、存档或事务一致性的错误。在业务允许且完整性可判断时，隔离异常项/步骤、保留有效结果，并返回可识别的部分成功或待恢复状态；不能静默丢数据、伪造默认值、把错误当空结果或宣称全部成功。无法保证正确性时停止受影响的操作或原子事务，保持可恢复状态，让无依赖的功能继续。不能靠全局捕获后继续写入来维持表面可用。
- **集合数据保持正常项可用**：集合查询、解析、转换、关联补全、刷新、展示和批量操作必须识别单项异常的边界。正确性允许时跳过、隐藏或局部标记坏项，正常项继续刷新、展示和操作；不能因一个对象缺失、某条数据异常或单项请求失败，让整个列表、整批独立操作或无依赖功能不可用。例如异常视频不阻断其他视频播放和留言，异常邮件不阻断正常邮件展示和领取，排名关联用户缺失时只隐藏该行或显示“无法加载”。单项隔离不能改变分页结束条件、伪造业务值、丢弃仍需处理的业务记录或误报整批完成；保留错误定位与必要恢复依据。整次刷新失败时保留仍有效的展示，账号/权限已失效的数据除外；涉及鉴权、关键数据或原子事务时停止其负责范围内的操作，不能继续不安全的写入。设计和审查修复建议时都要检查上述后果。
- **性能按实际规模核对**：估算调用频率、数据量、算法复杂度、内存/分配、主线程耗时和额外网络/存储往返；复用已有校验与批量入口，避免逐条请求、反复全量扫描、无界重试和日志放大。有既定预算则按预算验证；热点或明显成本变化使用代表性与边界规模测量，没有测量不得声称性能达标。低影响修改不强制建设基准平台。
- **验证收益与失败影响**：按风险使用项目已有的最小验证入口，覆盖正常有效数据不会被误拒、真实坏数据不会污染状态、单项失败不会扩散，以及相关并发/失效条件。涉及集合处理时，至少核对一个坏项夹在正常项中、批量中途失败、整次刷新失败及受影响的分页边界；验证正常项继续处理、错误项可识别、已确认成功不被抹掉，不能只证明新增检查会报错。涉及性能变化时记录规模和耗时/请求量等实际证据。不能让防护造成比原问题更严重的后果；不要求每次改动穷举无关场景，未执行的验证如实记录。

## 逻辑改动后的关联审查

每次新增逻辑接入正式链路、修改、修复或重构逻辑后，都必须执行关联审查，无需用户另外要求。改动小、签名不变或相关文件没有 diff，都不能免除检查。纯文案、注释或格式变化确实不改变逻辑与数据合同时，沿对应文档检查处理。

1. **固定行为差异**：从本次真实 diff 和有效需求说明改了哪些输入、输出、错误语义、副作用、时序或生命周期，以及哪些旧行为仍须保持。重构也要核对这些合同，而不只看代码是否能编译。
2. **追踪全部受影响关系**：读取修改点的调用者、被调用依赖与共享数据拥有者，沿真实依赖继续检查直接及间接链路。覆盖适用的事件发布/订阅、注册/导出、配置/资源/序列化引用、异步回调、持久化/协议、缓存与索引等入口；不能只搜索函数名、只读当前文件或固定查一层。共享逻辑的所有受影响调用场景都要纳入，包括未修改的模块、表现入口和旧数据兼容路径。
3. **逐链路核对合同**：比较改前改后对调用方假设、状态转换、数据一致性、失败影响范围和资源释放的影响。根据本次变化检查重复执行、并发/取消/迟到回调、事件顺序、缓存失效、锁释放和性能等适用风险，不能把问题从当前函数转移到其它入口。
4. **确定覆盖边界**：每条已确认受影响的链路都有审查结论与代码、配置或资源依据；共用链路可复用同一结论。沿依赖追踪至变化不再传播的稳定合同边界，并说明停止依据；不能凭“另一个模块没改”排除，也不把“相关”扩大为无依据的全仓扫描。
5. **修复并重新审查**：在原授权内处理本次引入的缺陷和为正确完成改动所必需的连带修复；修复后重新检查最终 diff 及受影响关系，直到已识别的本次回归问题解决。无关历史问题单独记录，不借此扩大改造；重要既有逻辑的高影响疑点按巡检技能的详细模式处理。确需业务决定时明确该项，继续独立工作。
6. **验证关联行为**：使用项目已有且匹配的回归入口，覆盖改动后的目标行为、受影响的既有调用场景，以及本次相关的失败/边界条件；同一用例可覆盖共用链路。发现测试失败先定位、修复并重跑，修复后复核连带影响。按风险决定是否补测试，不为每个函数机械新增用例，也不以削弱断言、只检查新函数或仅编译通过宣称关联逻辑正常。
7. **按证据收尾**：简述改动点、关联范围及覆盖依据、发现与处置、实际验证和剩余缺口；普通小改动不要求另建完整报告。环境或资料缺失时继续可完成的检查，并明确未验证的链路及其影响，不能将未覆盖、未运行或“暂未发现问题”写成已保证没有新 bug。

### 公共与底层逻辑的兼容性

修改共用工具、基类、组件、对象池、存储/同步入口或公共 API 时，先按真实引用列全使用方与使用方式，逐项给出兼容结论。必须包含其它功能、不同配置/资源变体、派生/重写实现及间接调用；签名未变、旧动效停用或原问题已消失，都不证明其他使用方兼容。

- **明确共用合同**：核对默认值、参数含义、初始化/重置/回收、事件时序、状态拥有权及副作用。区分模板默认值、实例原有值和调用方按本次业务配置的有效值，不能假定重置到模板就对所有使用方正确。
- **防止局部修复改变其它业务**：例如为修复一个弹窗而调整公共对象池，须检查进度条、列表单元等同池使用方的缩放、显隐、绑定和复用状态。停用旧动画只影响该动画入口，不能据此删除仍由其它入口维护或使用的状态。必要业务差异由正确拥有者或明确配置表达，不在底层按业务名加特例或另留一套实现。
- **逐使用方验证兼容**：按实际合同覆盖首次创建、回收再取、不同调用方交替复用，以及与本次相关的关闭重开、取消或迟到回调。既验证原问题得到修复，也验证其它使用方原有效果和数据仍正确；不同合同与变体分别核对，共用且条件相同的证据可复用。
- **闭合连带影响**：基础行为确需变化时，在同一次改动适配受影响使用方及相应资源/配置，保留仍需的最小兼容入口，并更新改变的接口说明和注释。使用方清单或合同不完整时保留具体缺口，不能只测一个调用者便宣称公共改动兼容。

## 新旧逻辑、归档和兼容

### 先确定待退役范围

找到旧逻辑的调用点、注册、导出、配置键、资源引用、文档和测试；区分整文件退役与同文件局部替换。读取精确 diff，保护用户及无关的未提交改动。旧代码是否有 bug、是否有保留价值，不是删除无关工作成果的授权。

### 按实际状态处理

1. **仍需运行时兼容**：旧 API、存档、序列化资源或外部调用仍可能到达时，只留转换/转发到新逻辑的最小兼容层，不保留第二套业务规则。用 `Obsolete`、`@deprecated` 或紧邻注释标明已过时、替代入口、触发版本/条件、删除条件和最晚删除版本；未采用版本号的项目使用明确移除里程碑，不编造版本。
2. **无需兼容，待删内容可由版本历史恢复**：核对目标文件实际被 Git、SVN 或项目所用软件跟踪，且待删除的内容确实存在于可读取的历史中；直接删除旧逻辑，不创建 `archive/`。仅存在仓库或文件曾有历史不够；检查目标的跟踪/忽略状态及具体版本，不能仅凭目录名或忽略规则判断已跟踪文件。
3. **已跟踪，但当前旧内容含未入历史的差异**：不能把它当作已有可恢复历史直接删除，也不为绕过判断自动创建归档。先核对差异归属和本次授权；用户明确不要的差异可按授权删除。去留不明确时，只暂停这部分并确认，继续不受影响的工作；不能擅自提交、回退或丢弃差异。
4. **目标未纳入版本控制或被忽略，且无可用历史**：只有旧逻辑已确认无 bug、正常运行，并且作为完整旧版本有保留价值时才归档。正常运行依据已有运行记录或相关验证，不把缺少证据说成已验证。
5. **无需兼容且属于有 bug、无法确认正常运行、临时、重复或无保留价值的旧逻辑**：在已确认的任务范围内直接删除，不归档；仍须遵守上述用户改动保护要求。

### 归档方法与同文件替换

归档放在项目根目录 `archive/`，完整镜像相对项目根目录的路径；不改文件名、扩展名或层级。例如 `Assets/Test.txt` → `archive/Assets/Test.txt`。

- **整文件退役**：移动原文件，不在活跃目录复制保留另一份旧实现。
- **同文件替换，尚有经过确认的完整旧版**：替换前可将该完整旧文件移入镜像归档路径，再在原路径写入只含新逻辑及仍需保留内容的文件；当前正式入口不能丢失。
- **已经混合新旧逻辑**：不能整文件搬走仍活跃的新逻辑，也不能把摘出的几个函数冒充正常完整旧版。先找是否有符合条件的完整旧版；没有时不伪造归档，按上述分类处理旧段并保留新段。若要丢弃的用户差异去留不明，确认该部分处置。
- 归档目标已存在时不覆盖已有历史；停止该文件的归档并确认保留方式，不擅改镜像规则或制造 `Backup2` 副本。
- `archive/` 排除编译、资源打包、代码生成、自动发现和正式入口索引；归档说明记录原路径、替代入口/版本、归档原因、正常运行依据及恢复方式。按项目资源机制处理关联元数据，不能破坏活跃资源引用。

### 同一次改动完成收尾

删除或迁移旧调用、注册、导出、配置键、资源引用和文档入口。仍覆盖有效业务行为的测试迁移到新逻辑；仅服务已退役实现的测试才删除。用相关构建、资源检查及行为测试确认正式路径只有新逻辑，仍需的最小兼容入口另行验证。

过时标记不是把整段实现注释掉。不得留下没有去向的 `Old`、`New2`、`Backup`、`Temp`、`Legacy` 文件、永久关闭的 feature flag 或“以后可能用”的死逻辑。灰度和回滚复用项目已有发布机制，明确结束条件。

## 日志和操作锁

触及关键操作、数据变动、日志或多来源锁定时，按 [日志记录与操作锁定](operation-logging-and-lock-coordination.md) 核对统一入口、数据源/堆栈追踪及逐次释放；不以本文件的普通错误日志建议替代专项规则。

## 注释和验证

- 注释解释原因、约束、非直观取舍或外部协议，不复述代码；修改行为时同步更新或删除过期注释。
- 新增或修改行为时，运行项目已有的最小相关格式化检查、静态检查、编译和测试。修复缺陷优先补可复现该行为的测试，不只断言私有实现细节。
- 检查与任务相匹配：数据扩展验证实际新增数据，持久化验证独立回读，异步状态验证失败/取消；专项验证使用对应参考，不对每个小改动运行所有场景。
- 无法运行时说明命令、缺少的依赖/环境和未覆盖部分；不能把“存在测试文件”“读过验证脚本”或关键词命中当作检查通过。
- 默认不新增 Hook。只有确定检查反复漏检、且已有通过/失败/不适用案例时，才在授权范围考虑自动触发；不能用关键词 Hook 代替设计判断或扩大修改权限。
