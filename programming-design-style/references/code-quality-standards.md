# 代码质量基线

本文件只规定项目没有更具体规则时的最低要求。语言、框架、团队格式化器、linter、类型检查器、目录结构和已有公开 API 约定优先；不要用本文件强迫所有项目采用同一种命名、异常、可空或异步写法。

## 先确认项目约定

实施或评审前检查目标范围内的格式化、静态检查和测试入口，例如 `.editorconfig`、formatter/linter 配置、编译器选项、测试配置、同目录的既有范式和 CI 脚本。已有自动规则时，按它们格式化并运行相关检查；不要自行扩大为全仓重排或顺手改造。

## 文件、类型和公开边界

- 一个文件的主要类型或功能应能从文件名看出；文件内辅助类型只服务该主功能。不要在无关功能之间塞“顺手通用”的工具。
- 类型、函数、变量和参数名称表达业务含义、单位、集合性或布尔判断，不使用无意义缩写、误导性名称或与职责无关的历史名称。布尔值、谓词和条件分支应读得出成立条件；集合、单项、时间/数量和键/显示名要能区分。
- 公开方法、事件、命令和数据结构必须说清输入、结果、失败方式及副作用。能保持私有的成员不要扩大可见性；不要为了“方便调用”暴露可被任意修改的内部状态。
- 新增抽象只在消除真实重复、隔离不稳定依赖、收窄公开边界或改善测试时引入。不能用只有一次调用、没有业务名字的包装层代替直接清晰的调用。

## 函数和控制流

- 每个函数围绕一个可说明的动作或查询。函数同时做校验、状态变更、持久化、通知和 UI 操作时，优先保留一个业务编排入口，并把可独立理解的步骤抽为命名明确的私有方法或已有模块调用。
- 条件使用提前返回或清晰分支减少嵌套；不要为了压缩行数写难读的复合条件、三元链或依赖副作用的短路表达式。
- 不要让参数、全局状态、集合或传入对象在调用方难以发现的情况下被修改。必要的修改应通过名称、返回值、命令对象或 API 契约明确；查询方法不应悄悄写入业务状态。
- 删除无效分支、注释掉的旧实现、不可达代码、无意义的临时变量和已经失效的兼容路径。保留兼容路径时，写明触发条件、移除条件和正式入口。

## 数据、错误和异步

- 可空、缺失、失败、未加载和空集合是不同状态时，不能都用 `null`、`false` 或魔法返回值混在一起。使用项目已有的结果类型、错误码、异常或显式状态表达。
- 不吞掉异常、不只记录后继续假装成功，也不把预期业务失败当作无上下文的通用异常。错误信息包含对排障有用的操作和身份，不记录不必要的敏感数据。
- 异步操作、取消、超时和资源释放遵从项目已有模式。不能启动未观察的后台任务；状态变更在成功、失败和取消后都要保持一致。
- 跨处复用的符号值、可扩展内容和配置读取按 [数据驱动与数据归属](data-ownership-and-workflows.md) 判断，不在这里另维护一套字面量规则。

## 新旧逻辑、归档和兼容

### 先确定待退役范围

找到旧逻辑的调用点、注册、导出、配置键、资源引用、文档和测试；区分整文件退役与同文件局部替换。读取精确 diff，保护用户及无关的未提交改动。旧代码是否有 bug、是否有保留价值，不是删除无关工作成果的授权。

### 按实际状态处理

1. **仍需运行时兼容**：旧 API、存档、序列化资源或外部调用仍可能到达时，只留转换/转发到新逻辑的最小兼容层，不保留第二套业务规则。用 `Obsolete`、`@deprecated` 或紧邻注释标明已过时、替代入口、触发版本/条件、删除条件和最晚删除版本；未采用版本号的项目使用明确移除里程碑，不编造版本。
2. **无需兼容，待删内容可由版本历史恢复**：核对目标文件实际被 Git、SVN 或项目所用软件跟踪，且待删除的内容确实存在于可读取的历史中；直接删除旧逻辑，不创建 `archive/`。仅存在仓库或文件曾有历史不够；检查目标的跟踪/忽略状态及具体版本，不能仅凭目录名或忽略规则判断已跟踪文件。
3. **已跟踪，但当前旧内容含未入历史的差异**：不能把它当作已有可恢复历史直接删除，也不为绕过判断自动创建归档。先核对差异归属和本次授权；用户明确不要的差异可按授权删除。去留不明确时，只暂停这部分并确认，继续不受影响的工作；不能擅自提交、回退或丢弃差异。
4. **目标未纳入版本控制或被忽略，且无可用历史**：只有旧逻辑已确认无 bug、正常运行，并且作为完整旧版本有保留价值时才归档。正常运行依据已有运行记录或相关验证，不把缺少证据说成已验证。
5. **无需兼容且属于有 bug、无法确认正常运行、临时、重复或无保留价值的旧逻辑**：在已确认的任务范围内直接删除，不归档；仍须遵守上述用户改动保护要求。

### 归档方法与同文件替换

归档放在项目根目录 `archive/`，完整镜像相对项目根目录的路径；不改文件名、扩展名或层级。例如 `Assets/Test.txt` → `archive/Assets/Test.txt`。

- **整文件退役**：移动原文件，不在活跃目录复制保留另一份旧实现。
- **同文件替换，尚有经过确认的完整旧版**：替换前可将该完整旧文件移入镜像归档路径，再在原路径写入只含新逻辑及仍需保留内容的文件；当前正式入口不能丢失。
- **已经混合新旧逻辑**：不能整文件搬走仍活跃的新逻辑，也不能把摘出的几个函数冒充正常完整旧版。先找是否有符合条件的完整旧版；没有时不伪造归档，按上述分类处理旧段并保留新段。若要丢弃的用户差异去留不明，确认该部分处置。
- 归档目标已存在时不覆盖已有历史；停止该文件的归档并确认保留方式，不擅改镜像规则或制造 `Backup2` 副本。
- `archive/` 排除编译、资源打包、代码生成、自动发现和正式入口索引；归档说明记录原路径、替代入口/版本、归档原因、正常运行依据及恢复方式。按项目资源机制处理关联元数据，不能破坏活跃资源引用。

### 同一次改动完成收尾

删除或迁移旧调用、注册、导出、配置键、资源引用和文档入口。仍覆盖有效业务行为的测试迁移到新逻辑；仅服务已退役实现的测试才删除。用相关构建、资源检查及行为测试确认正式路径只有新逻辑，仍需的最小兼容入口另行验证。

过时标记不是把整段实现注释掉。不得留下没有去向的 `Old`、`New2`、`Backup`、`Temp`、`Legacy` 文件、永久关闭的 feature flag 或“以后可能用”的死逻辑。灰度和回滚复用项目已有发布机制，明确结束条件。

## 日志和操作锁

触及关键操作、数据变动、日志或多来源锁定时，按 [操作日志与协作锁](operation-logging-and-lock-coordination.md) 核对统一入口、数据源/堆栈追踪及逐次释放；不以本文件的普通错误日志建议替代专项规则。

## 注释和验证

- 注释解释原因、约束、非直观取舍或外部协议，不复述代码；修改行为时同步更新或删除过期注释。
- 新增或修改行为时，运行项目已有的最小相关格式化检查、静态检查、编译和测试。修复缺陷优先补可复现该行为的测试，不只断言私有实现细节。
- 检查与任务相匹配：数据扩展验证实际新增数据，持久化验证独立回读，异步状态验证失败/取消；专项验证使用对应参考，不对每个小改动运行所有场景。
- 无法运行时说明命令、缺少的依赖/环境和未覆盖部分；不能把“存在测试文件”“读过验证脚本”或关键词命中当作检查通过。
- 默认不新增 Hook。只有确定检查反复漏检、且已有通过/失败/不适用案例时，才在授权范围考虑自动触发；不能用关键词 Hook 代替设计判断或扩大修改权限。
