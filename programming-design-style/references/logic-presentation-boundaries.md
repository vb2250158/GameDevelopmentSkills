# 逻辑与表现统一范式

任务涉及游戏引擎组件、UI、Web、桌面、托盘、移动端、编辑器或其他表现入口时，用本参考完成设计与巡检。核心范式相同，具体协作方式按项目形态选择。

## 职责归类

| 归稳定逻辑拥有者 | 归表现 / 引擎适配 |
| --- | --- |
| 业务事实、状态含义、规则、权限、校验 | 布局、组件、颜色、动画、文案格式 |
| 查询与命令、持久化、迁移、跨端一致性 | 展开、选中、焦点、加载等短暂交互状态 |
| 会影响可执行动作或最终结果的派生 | 可从领域 DTO 重建的 presentation model |
| 失败、重试、冲突、存档和同步语义 | 错误、缓存时间和不可用状态的展示 |

## 同一范式的不同载体

- 单机游戏：纯逻辑模块拥有规则和运行状态；MonoBehaviour、Actor、Node、Component 连接输入、场景生命周期、动画和特效。可直接方法调用或事件协作。
- 本地桌面工具：本地 Service、Repository 或文件管理模块拥有数据；窗口组件负责交互和展示。
- Web / 多客户端应用：领域模块或服务端拥有业务事实；客户端通过共享库、IPC 或 API 获取和提交数据。

不要因“分层”预设必须有网络、DTO、Service、依赖注入或事件总线。只有当抽象能改善拥有权、替换性、复用性或验证时才增加。

## 数据入口与表现反馈

状态定义、真实写入和展示快照按 [数据驱动与数据归属](data-ownership-and-workflows.md) 处理。不能因为客户端和业务模块分了目录，就认定没有重复状态与规则。

业务层产出结果和表现意图；表现层将反馈组织成可排序、可组合、可跳过或可回放的动作列表。按实际需要复用已有调度，简单刷新可直接方法/事件完成，不为一个反馈新造调度框架。表现资源映射由数据维护，业务层不散落调用具体动画和特效。

通用工具、第三方适配、业务模块、运行时组件、UI 和编辑器能力按职责放置；底层工具不反向依赖具体业务，模块不直接改别人的内部状态。事件/命令及参数由受控入口定义，不能用事件掩盖对私有时序的依赖。

## 开工前边界与复用判断

按任务复杂度确认；简单单进程功能简短说明前三项即可，不固定生成表格：

1. 需求能力与业务事实拥有者。
2. 表现入口需要哪些生命周期、交互和渲染职责。
3. 两者用直接方法、事件、共享库、Repository、IPC 还是 API 协作，为什么这是当前最简单合适的方式。
4. 现有逻辑模块和其他表现入口如何复用。
5. 新增抽象或新逻辑拥有者能带来什么明确价值。

没有现有拥有者时可以新增逻辑模块；不要把新业务规则顺手塞进当前引擎组件或 UI。

## 常见设计矛盾

- 引擎组件或 UI 直接拥有本应由逻辑模块维护的正式业务状态、配置解析、存档或规则。
- Web、桌面、托盘、移动端或多个游戏表现组件分别实现同一业务能力。
- 接入 API 后仍保留本地 Repository、旧类型或打包依赖，形成隐蔽双入口。
- engine component / view model 决定业务状态、可执行动作、持久化结果或跨表现语义。
- 只搜索当前表现目录，因附近存在旧旁路就继续扩展，没有检查逻辑模块和其他表现入口。
- 项目文档描述旧做法，Agent 未用真实 API、调用链和提交历史交叉验证。
- 为了形式分层强造多层 Service、DTO、事件或网络边界，反而让简单同进程调用更难理解和验证。

## 接口不足与失败处理

逻辑入口缺能力时，先扩展业务拥有者，再让表现层复用。不要只给某个引擎组件或客户端增加旁路补丁。

远程服务不可用时，显示明确错误，或使用标明时间、只读属性和失效规则的缓存。不得静默切换为表现层直读底层数据。只有产品明确要求离线模式，并设计同步、冲突解决和最终解释权时，才允许独立本地数据路径。

## 按目标验证

- 逻辑测试：业务规则脱离 Unity/Unreal/Godot/Qt/React 等表现环境也能验证。
- 真实写入：从表现入口修改后，通过拥有者独立读取，并从另一个入口或重新打开界面核对；不能只断言 UI 对象已变化。
- 架构检查：表现层不复制业务规则，不直接维护逻辑拥有者的数据源。
- 替换测试：更换引擎组件、UI 或客户端表现时，稳定逻辑模块不需要修改。
- 适度设计检查：删除中间层后若职责仍清楚且没有重复复杂度，说明该层可能没有价值。
- 失败测试：远程入口不可用时不会启用隐蔽旁路或制造第二事实源。
- 替换旧逻辑时：按 [退役规则](code-quality-standards.md#新旧逻辑归档和兼容) 检查关联打包/资源入口，保留的最小兼容层单独验证。
