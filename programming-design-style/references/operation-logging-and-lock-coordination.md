# 日志记录与操作锁定

用于关键操作、业务数据变动和排障日志，以及输入、黑屏、相机的锁定与释放。操作锁定指多个流程共同限制同一操作时，每次获取独立释放，最后一个有效锁释放后才恢复操作。日志首先帮助人和 agent 找 Bug；不要求新建审计平台、远程日志服务或分布式锁。

## 统一日志入口

先查项目日志工具、调试控制台、错误上报、日志配置和已有采集方式。必须复用统一入口；能力不足时在该入口补充，不在各模块混用临时打印和不同后端。没有可用入口时，建立与项目规模相称的最小日志接口。

统一入口至少支持日志分组、级别、开启/关闭、按组筛选和诊断堆栈采集。分组和开关走现有配置/注册入口，不在业务分支散落 `if (debug)`。可能扩展的日志组定义按 [数据驱动规则](data-ownership-and-workflows.md) 维护。关闭日志或调整诊断级别不改变业务结果。

## 日志关闭时的性能要求

日志关闭后的额外成本应接近一次布尔判断，且不产生日志相关的每次调用分配。复用统一入口维护的有效开关；日志组、级别及配置的组合判断在配置变化时更新，不在每条日志调用时重复查配置、查字典或构造筛选条件。用于提前短路的开关必须来自统一日志入口，不能另存一套业务调试状态。

- **延迟计算**：优先使用委托、消息工厂或平台支持的等价惰性机制。字符串拼接、插值、格式化、`ToString()`、诊断字段计算、对象遍历、序列化、路径构造、堆栈采集和日志入队都在确认开启后才执行。把已拼好的字符串包进委托，或先计算参数再传给日志函数，不符合要求。
- **避免闭包成本**：消息延迟生成不等于调用零分配。检查捕获闭包、委托实例、装箱及 `params` 数组是否在开关判断前创建；优先复用缓存的无捕获委托，或使用无装箱的显式状态传递等现有机制。必须捕获上下文时，将捕获和构造隔离到仅在开启后调用的函数，核对编译产物或运行分配，不能仅凭 lambda 写在 `if` 内就认定没有分配。
- **函数内提前返回**：普通日志函数若接收已计算的字符串或参数，函数内部再判断开关已经太晚。关闭路径必须在调用方生成诊断内容之前短路，或由真正惰性的接口控制计算；仅将字符串拼接搬进另一个会无条件调用的函数也不符合要求。
- **不改变业务**：惰性委托只读取诊断所需信息，不承担业务状态修改、必要数据读取或事务操作；开关变化不能改变业务结果。开启后的采集、格式化和输出仍按日志组及限频要求控制成本。

## 调试日志的命名与补充

日志组使用稳定的功能名称；文本消息使用 `[功能名称]` 前缀，方便筛选。前缀、级别和输出仍由统一入口管理，不在业务代码旁路调用控制台打印。

先用已有日志、异常堆栈、代码和配置定位问题；仍有证据缺口时，补充能区分具体假设的记录。记录设计写明文件/方法及可核实的行号、触发时机、事件和字段、预期分支结果，以及要验证的问题；同时明确开关、限频、敏感信息处理和运行成本。级别按项目现有定义选择，正常流程、可恢复异常和实际失败分别记录。

修复后复现相关操作，结合实际结果和日志核对假设；证据不足时调整观察位置与字段。临时诊断记录完成用途后清理，长期排障所需记录纳入既有分组与开关。

## 关键操作记录什么

关键操作和实际数据变动必须接入日志，在调用/执行边界记录开始与结果；结果包括成功、业务拒绝、失败、异常或取消。数据变动记录正式提交的结果，不能把尝试写入记成已完成；必要时带变更前后摘要或版本。

| 诊断问题 | 需要的记录 |
| --- | --- |
| 谁发起、属于哪次操作 | 操作名、日志组、关联标识、调用者和必要的父调用关系 |
| 到了哪个真实数据源 | 业务拥有者、读写方法、实际使用的存档/表/文件/资源或数据源标识、目标对象 |
| 改了什么、结果如何 | 变更摘要/版本、结果或错误、必要耗时 |
| 为什么走到这里 | 关键调用位置、源头读写/变更栈、异常原始堆栈 |

数据源标识来自实际读写入口，不能只打印调用方猜测的来源。记录必要的非敏感路径、表/资源标识，不能输出带凭据的连接信息或完整个人载荷。token、密码和 cookie 不原样写日志；不强制每次修改增加独立脱敏测试，涉及敏感字段或日志处理变化时再做相应检查。

## 调用堆栈与跨边界关联

诊断组开启后，关键数据读写、状态变更和异常必须能定位实际调用者、真实数据源及关键调用堆栈，不能只有“保存失败”或孤立的关联 ID。

- **同进程**：在关键源头读写/变更位置采集堆栈，保留模块、方法和可取得的文件/行号；捕获异常时保留原始异常栈，不重新包装成丢失来源的文本。
- **异步或跨进程**：传递关联标识及上下游关系，在各边界记录调用位置、局部堆栈和结果，再还原操作链。不能声称一段普通调用栈覆盖了网络或异步边界，也不能只记下游接收栈却丢失发起者。
- **符号与性能**：按日志组开启详细堆栈采集，不在每帧无目的打印。批量记录批次和计数，按对象/操作选择诊断范围；已选中的故障操作要能完整追踪，不能被采样截断。符号或 sourcemap 不可用时明确缺失，不编造行号。

应能沿“用户操作 → 命令 → 业务判断 → 正式数据源读写 → 返回/事件 → 界面采用的数据”定位问题。只有前端更新而未真实写入、读到了错误数据源或界面未刷新，都应能通过对应边界记录区分。

## 日志验证

按本次变化选择成功和相应失败/取消场景，实际读取日志：能定位真实数据源，串起操作链，并取得关键堆栈；日志组关闭不输出该组，重新开启能恢复追踪。没有运行时日志或符号条件时，明确未验证范围，不用字段齐全代替链路可追踪。

涉及日志调用或入口实现变更时，验证关闭后消息工厂/诊断函数未执行，且没有新增的日志相关分配；对高频路径用代表性调用量对比无日志基线与关闭状态的耗时、分配量。重新开启后验证内容、关联和堆栈仍完整。不以“控制台没输出”或“用了委托”代替性能证据，未测量时注明性能未验证。

## 多来源操作锁

### 锁组、拥有者与逐次句柄

先复用项目锁定工具；同一组只要仍有任一有效获取就保持锁定，不同组互不影响。输入、黑屏、相机等表现入口只读取派生锁定状态，不直接写全局 `isLocked`。

每个调用方传稳定、可搜索的 `ownerKey` 表示业务原因；它不是显示文案、随机字符串、调用栈或数组位置。每次获取返回专属 lease/handle，并在该次调用的局部作用域保存。ownerKey 标识原因，句柄标识本次获取，不能混用；不能用一个“当前句柄”字段覆盖还在执行的旧调用。

- 同一 owner 重入使用独立句柄；内部可以引用计数，但计数不能替代逐次释放身份。
- 释放只能消耗自己的本次获取。重复释放同一句柄必须无副作用，不能再次扣减或释放别人的锁。
- 旧任务迟到回调、取消和 `finally` 重复触发都不能影响新获取；强制清理后也不能复用会被旧句柄命中的身份，可用失效标识或代次等已有机制保证。
- 最后一个有效获取释放后才解锁。禁止无 owner 的 `Unlock()`、跨模块清空锁组或“当前操作完成”后直接写 `isLocked = false`。

### 生命周期、诊断与验证

用 `finally`、`defer`、`using`、作用域清理或项目等价机制处理正常结束、失败、异常、取消、超时和销毁；跨帧/场景切换明确回收责任。必须全局清理时只由锁管理器执行，记录原因及受影响的获取，并使旧句柄失效。

获取、释放、重复释放、超时和回收接入统一日志组，记录锁组、ownerKey、句柄/关联标识、活跃获取数、原因和诊断调用来源。

触及锁定行为时至少验证：两个 owner 重叠；同 owner 重入；先后顺序颠倒；同句柄重复释放；清理后旧回调迟到；异常/取消/销毁释放；跨组隔离。目标组存在任一有效句柄时都不能提前解锁。

## 巡检证据

定位统一日志入口、组配置、源头读写位置和上下游关联；锁问题还需目标范围内全部获取/释放点、句柄生命周期和状态订阅者。没有调用链、运行记录或行级证据时列为待确认，不直接断言存在永久锁定、提前解锁或日志可用。
