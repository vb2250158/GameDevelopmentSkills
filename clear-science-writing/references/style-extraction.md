# 提取文风并绑定到 Codex 输出

这份参考处理“内容怎样呈现”。词汇是第一风格约束；句式、段落和整篇编排构成从小到大的其余层级，节奏、声音、情绪和表现策略横跨其中。文风不等于少数金句或单篇文章的表面特征。

提取时遵守同一判断链：先记录可观察写法，再推定阅读效果，再寻找跨样本稳定组合，最后判断它在什么读者、媒介和风险场景下适用。不能先写“冷静、正式、强硬”，再回头挑几个例子证明。

## 先确定文风使用的语言

从语料本身确定 `StyleProfile` 的默认语言：中文语料生成中文档案，英文语料生成英文档案。不要因为当前 Agent 用中文思考、用户用另一种语言提问，或参考模板是中文，就把英文语料的提取结果写成中文。混合语料先分组，只让与目标文体、受众和用途一致的那一组决定语言与风格；只有用户明确要求时才翻译或生成双语版本。

翻译不是机械替换。用户要求改用另一种语言时，保留叙述距离、推理顺序、句式张力、段落动作和语气强度，在目标语言中重新实现；不要硬搬只属于源语言的虚词、语序、押韵或双关。

## 选对样本

只把文体、读者和目的相近的完整文章放在同一组。例如，技术说明、公众科普、观点文章和文学散文应分开。每组优先收集来源、作者和用途清楚的多篇文本；网页自称“满分”或“爆款”只是标签，不是质量证明。

不整篇复制受版权保护的样本。保留链接、来源、用途和分析笔记即可。

语料过大时先固定种子抽取 100–300 个有效段落，完成词类发现和上下文判断；如果前中后段、不同文档或不同说话场景差异明显，使用分层采样。样本用于发现候选规则，全文统计用于验证规则，二者不能互相替代。

## 先提取词汇

完整读取 [lexical-extraction.md](lexical-extraction.md)，先完成逐类词汇统计，再生成 `LexicalProfile`。分类表只是搜索参考；输出必须具体说明实际语料在每一类主要使用什么、较少使用什么、常放在哪里、怎样搭配，以及哪些类别没有观察到稳定词汇。

词频之外还要记录标准化频率、样本覆盖率、位置、搭配、功能、同义替代比例和对照组差异。再做一次开放词汇发现，寻找参考分类没有预设的高频短语与句首句末习惯。词汇在特定主题中集中出现，只能说明内容；它在多个主题中持续承担同一种作用，才可能说明文风。

## 从样本提取文风卡

先完整读取 [nonlexical-style-extraction.md](nonlexical-style-extraction.md)，生成 `NonLexicalStyleProfile`，再压缩为最终 `StyleProfile`。

逐篇标注，再找跨文本重复出现的选择。先按词汇、句式、段落和整篇编排记录证据；关系、确定、情绪、速度等阅读效果放在第二层判断：

| 维度 | 提取问题 |
| --- | --- |
| 词汇选择 | 哪些词、搭配、句首、句末和禁用项跨样本稳定；它们承担什么功能？ |
| 句式构造 | 句子在告知、询问、建议、要求还是拒绝；主语、责任、焦点、逻辑和节奏怎样处理？ |
| 段落结构 | 段首怎样进入，中间怎样展开，段尾怎样退出；哪些骨架持续出现？ |
| 整篇编排 | 读者先得到答案、背景、案例还是悬念；证据、反例、行动和结尾怎样排列？ |
| 阅读效果 | 正式、距离、权力、确定、行动压力、情绪、具体、精确、密度、速度和互动分别偏向哪里？ |
| 场景变化 | 哪些倾向平时保持，哪些只在高风险、私密、正式或叙事情境中改变？ |
| 排除项 | 哪些特征只是题材、人物立场、文体默认、单章集中或不可迁移内容？ |

词频必须连同位置、搭配和功能一起看。主题词的复现用于稳定讨论对象；功能词显示常用推理方式；具体动词和抽象名词的比例反映文章的动作感或分析感。不要把统计结果变成机械配额。

公开或普通调用使用的报告只保存统计、来源编号和短上下文说明；含原文句子、人物身份、私人路径和完整溯源的证据另存私人层，只有复核来源或更新提取时读取。

## 生成 StyleProfile

将跨文本稳定特征压成可执行配置；每项都应能在输出中检查。档案本身使用目标语言，并直接采用目标文风书写：克制的文风就用克制的句子，短促的文风就避免冗长解释，分析型文风就让规则呈现清楚的推理关系。不要一边把目标文风描述为“简洁”，一边用模板腔和抽象名词写出臃肿档案。

```text
StyleProfile
（以下字段名称与内容均使用目标语料语言，不默认中英并列）
适用范围：
目标读者与文体：
LexicalProfile：
NonLexicalStyleProfile：
词汇输出：
句式输出：
段落输出：
整篇编排：
言语行为与读者关系：
阅读效果轴：
主倾向与次倾向：
场景变化与触发条件：
三至五组声音指纹：
禁止项：
不可迁移项：
正向校准样例：
反向校准样例及失败层级：
```

示例不是要模仿某位作者，而是可检查的选择：

```text
词汇输出：保留核心术语；多用具体动词，少用抽象套词；核心词只在标题、段首、转折和结尾复现
句式输出：中句解释，短句收束；需要转向时用完整因果或转折句
段落输出：先事实或问题，再解释，再给行动或边界
整篇编排：答案先行；背景在需要时补入；结尾写行动和成立条件
言语行为与读者关系：面对非专业读者，直接但不过度口语化；普通问题用建议，高风险问题明确禁止
阅读效果轴：冷静、清楚，避免居高临下；具体但不伪造精确度
主倾向与次倾向：完整说明为主，短促行动句为辅
场景变化与触发条件：安全或不可逆损失出现时提高行动压力，不提高攻击性
三至五组声音指纹：具体动词 + 完整因果；中句解释 + 短句结论；结论先行 + 边界随后
禁止项：口号、连续反问、无依据的程度词
不可迁移项：来源人物立场、题材名词和故意错误
正向校准样例：使用当前任务的中性事实新写三至五句，不复制来源原句
反向校准样例及失败层级：用相同事实新写不符合版本，并指出问题在词汇、句式、段落还是整篇编排
```

最终档案只保留能执行、能检查的稳定结论。每个维度优先写一个主倾向和一个确有证据的次倾向，不把几十个维度都写成硬性配额。正反样例必须根据档案重新生成，只用于校准规则，不从受保护语料复制句子。

## 语言风格 Skill 的正式档案规范

建立五份档案前，完整读取 [four-layer-writing-contract.md](four-layer-writing-contract.md) 和 [four-layer-style-data-schema.md](four-layer-style-data-schema.md)。前者规定不可省略的分析维度，后者规定四层共同的数据结构；两者都不规定目标文风必须采用哪些技巧。每个维度都要留下状态，并建立参数词典：词汇保存实际词，句式保存实际结构，段落保存实际动作序列，整篇保存实际信息路线。四层参数同时写入 `style-data.json`，统一记录类型、频率、位置、组合和变化范围。只有目标语料支持的具体参数才能进入规则表和运行时档案。

提取结果需要长期复用或绑定到 Agent 时，默认建立以下五份档案：

| 文件 | 负责内容 | 普通运行是否加载 |
|---|---|---|
| `lexical-profile.md` | 各类型词语、同义选择、频率、覆盖、位置、搭配、功能、场景和禁用项 | 是；词汇是第一风格约束 |
| `sentence-profile.md` | 言语行为、主语与责任、焦点、条件和因果、否定、问句、命令、句长、断句和标点 | 由 `style-profile.md` 汇总；复核时完整读取 |
| `paragraph-profile.md` | 段首进入、中段展开、段尾退出、常见骨架、拆段、过渡和列表 | 由 `style-profile.md` 汇总；复核时完整读取 |
| `composition-profile.md` | 读者问题、答案位置、背景深度、证据与反例顺序、全文路线、行动和结尾 | 由 `style-profile.md` 汇总；复核时完整读取 |
| `style-profile.md` | 四层运行参数、主次倾向、变化触发、声音指纹、禁止项、不可迁移项和校准样例 | 是；作为统一运行时参数 |
| `style-data.json` | 四层客观参数、频率、位置、组合、变化范围及排行数据 | 否；供生成、复核和 HTML 使用 |

五份文件使用以下文件级合同：

| 文件 | 必须出现的结构 |
|---|---|
| `lexical-profile.md` | 目标语言与语料范围；逐类词典；规则 ID；实证词；状态；使用方式；频率、覆盖、位置、搭配或对照证据；置信度；未观察到和不可迁移类别 |
| `sentence-profile.md` | 规则 ID；规则类别；状态；适用范围；主次倾向；可观察证据；变化触发；混淆与例外；置信度；正反校准 |
| `paragraph-profile.md` | 与句式档案相同的规则字段；另写段首、展开、段尾、骨架、拆段、过渡和列表的适用性 |
| `composition-profile.md` | 与句式档案相同的规则字段；另写读者问题、答案、背景、证据、反例、行动和结尾的位置 |
| `style-profile.md` | 适用范围；分层验证状态；只含稳定或场景限定规则的“运行时规则”；规则 ID 回指；主次倾向；变化触发；三至五组声音指纹；禁止项；不可迁移项；正反校准与失败层级 |

生成 Skill 时还必须保存 `style-extraction-report.json`。它不是第六份风格档案，而是机器证据报告；至少包含 `context`、`layerMaturity`、`bodyStyleValidation`、带规则 ID 的 `observations`，以及 `sampleFullStability`、`holdoutReproduction`、`controlDiscrimination`、`oneVariableTests`、`forwardGeneration`、`contentPreservation`、`provenanceLeakage` 七项验证结果。每条 observation 必须保存规则类别、状态、适用性、主次倾向、证据、变化触发、混淆因素、验证结果和置信度，不能只写一个结论标签。每项验证必须是 `passed`，或在确实不适用时写成带原因的 `not_applicable`；未运行不能作为完成状态。

`bodyStyleValidation` 只审查面向人和 Agent 阅读的正文，不把标题、表格与表格数据、代码块、原始 JSON、导航和页面控件计入文风判断。审查范围至少包括目标 `SKILL.md`、五份正式档案、存在的答复与长文任务适配器，以及生成后的 HTML 正文。正文必须使用目标语料语言，并实际呈现词汇、句式、段落和整篇规则，不能只在表格里描述目标风格。独立任务完成复核后，保存版本、语言、所有被审查文件的正文哈希、整体源文件哈希、Markdown 与 HTML 正文哈希、四层审查结论和运行 ID；任何被审查文件改变后，旧记录必须失效。

`layerMaturity` 对词汇、句式、段落和整篇编排分别保存 `status`、`unitDefinition`、`corpusUnits`、`completedChecks`、`missingChecks` 与 `evidence`。`status` 只有 `complete`、`partial`、`insufficient` 三种；只有四层都为 `complete`，`overall` 才能为 `complete`。完成标准至少包括：词汇有分类、频率、覆盖、位置搭配、对照和复现；句式有句长分句、主语责任、焦点语序、言语行为、结构对照和人工复核；段落有可靠边界、段首、展开、段尾、骨架、拆段过渡和人工复核；整篇有足量完整文本、答案背景位置、证据反例顺序、全文路线、结尾合同、对照和人工复核。不满足的检查必须逐项列入 `missingChecks`，不能用前向写作测试替代来源提取证据。

生成或更新语言风格 Skill 时，还必须同步生成 `style-guide.html`。它是给人查看的独立阅读版和默认用户入口，不是第六份风格档案，也不是新的规则事实源。页面必须由 `SKILL.md`、五份正式档案和 `style-extraction-report.json` 自动生成；存在任务适配器或补充指标时可以一并展示。页面至少提供目录、全文搜索、分档案折叠、明暗切换和打印，不依赖外部脚本、样式、字体或图片。页面语言跟随语料语言，页面文案直接采用目标文风。

具体风格页面默认不重复讲解四层分类、提取方法、命名规则和验证合同。这些共同规则由 `clear-science-writing` 统一维护，并生成为 `references/language-style-standard.html`；读者需要时通过具体页面顶部的“通用规范”链接查看。具体页面只展示该风格实际使用什么词、怎样成句、怎样分段、怎样编排、规则何时变化以及验证结果。生成器不得把目标 `SKILL.md` 再展开成一个页面章节，以免把 Agent 执行说明和通用规范混进用户的风格参数阅读路径。

面向人的具体风格页面必须按固定阅读路线重组源档案：先看整体，再依次阅读词汇、句式、段落、整篇编排，随后说明四层怎样共同使用，最后进入复核区。文件边界不能决定页面顺序。四个层级使用同一信息结构：主要特征；具体类型与表达方式；常见组合或骨架；场景变化；正反样例；数据与文本依据；置信度、未验证项和不能推出的结论。不能让词汇层有完整分类，而句式、段落和整篇只保留概括。

每一层的实际结论后面必须就近附上可展开的“数据、文本依据与证据边界”。依据至少包含可观察事实、样本和全文范围、标准化频率或结构指标、覆盖率、位置和搭配、同文体或同场景对照、混淆因素、规则状态、验证结果和置信度；不适用于某一层的指标明确标为不适用。段落和整篇没有足够完整样本或人工标注时，仍展示其应分析的类型和候选骨架，但明确标注证据不足，不能把任务适配器写成来源风格。

这里的“有依据”指可追溯、可复算、可对照和可证伪，不是使用“科学证明”一类笼统措辞。一个词出现次数多，只能证明它常见；还需要覆盖、位置、搭配、对照和上下文功能，才能判断它是否具有风格区分度。句式、段落和整篇必须分别保留自己的可观察指标和人工标注依据，不能从词汇统计直接跨层推出结论。

五份 Markdown 档案和 JSON 报告改变后，必须重新生成 HTML。专用校验需要比较当前源文件与 HTML 的同步指纹；过期、手工复制、缺少正式档案或依赖外部资源的 HTML 都不能通过。Agent 普通运行不读取 HTML，避免它与正式档案形成重复上下文；用户查看、评审、打印或导出 PDF 时用系统浏览器打开它。不要把 Codex 源码查看器或文件预览当作 HTML 交付，因为这类预览可能禁用链接与脚本。除非用户主动要求原始档案，默认只向用户提供 HTML 入口。

`forwardGeneration` 对生成出的语言风格 Skill 始终适用，不能标为 `not_applicable`。通过时必须在 `evidence.runs` 中至少保存一条短答和一条长文记录。每条记录包含独立执行方式、运行 ID、原始中性任务摘要、结果摘要、通过状态、内容保持结果和来源泄漏结果。执行者必须是全新子 Agent 或独立任务；同一 Agent 的自我校准不能冒充独立前向测试。

需要完整机器词典和逐项指标时，另存 `lexical-metrics.json`。含原文、来源身份、私人路径或完整上下文的证据放在独立溯源层，普通 Skill 不加载。

每条分层规则采用统一记录方式：

```text
规则 ID：
规则类别：语料观察 | 风格推断 | 任务适配 | 通用约束
状态：稳定 | 场景限定 | 暂定 | 否决
适用范围：
主要倾向：
次要倾向：
可观察事实与证据引用：
风格推断与输出规则：
变化触发条件：
避免方式：
混淆因素与例外：
验证结果与置信度：
```

四种规则不能混写：

- `语料观察` 只说明出现了什么，不用“应当”把观察改成命令；
- `风格推断` 必须回指观察证据，并说明适用场景、混淆因素和置信度；
- `任务适配` 说明怎样把风格用于答复、调查或文档，不宣称来自语料；
- `通用约束` 保存事实、安全、权限和人的权益要求，它始终优先，但不能进入声音指纹或用于证明风格名称。

`style-profile.md` 的运行时规则必须通过规则 ID 回指前四份档案。`稳定`规则可以直接进入；每条 `场景限定` 的来源规则和运行时规则都必须写出自己的触发条件；`暂定`、`否决`和`证据不足`只能留在分层档案及证据报告，不能进入运行时规则或声音指纹。三至五组声音指纹必须逐项回指已经存在的运行时规则 ID，不能只写一组无法追溯的形容词或组合。

前四份档案是各层证据和状态的事实源，`style-profile.md` 是运行时汇总，任务适配器只说明如何用于答复或文档。旧入口需要继续兼容时，可以保留简短适配页并链接到总参数；不要复制整套规则形成第二个事实源。

生成出的 `SKILL.md` 必须从一层链接直接指向五份正式档案、`style-extraction-report.json` 和 `style-guide.html`，并说明何时读取：普通运行读取 `lexical-profile.md` 与 `style-profile.md`；解释、复核或更新时读取句式、段落、整篇及机器证据；任务适配器按任务加载；用户需要浏览、搜索或打印整套档案时打开 HTML。引用不能只藏在另一份参考文件里。

超过 100 行的参考档案在顶部提供索引。所有面向人的档案使用目标语料语言与目标文风；固定文件名、规则 ID、JSON 键、命令和代码保持机器合同。

## 创建与验证语言风格 Skill

创建新 Skill 时遵循 `skill-creator` 的生命周期，不手工拼出一个无法验证的文件夹：

1. 使用本 Skill 的初始化封装；它内部调用 `skill-creator/scripts/init_skill.py`，并按语料语言生成五份档案骨架：

   ```powershell
   node scripts/init-language-style-skill.mjs <skill-name> --path <输出目录> --display-name <正式名称> --language <zh|en> --description <触发说明>
   ```

2. 完成语料提取，替换全部占位内容。不要让“待提取、TODO、To extract”进入最终 Skill。
3. 根据最终 `SKILL.md` 重新核对 `display_name`、`short_description` 和 `default_prompt`；metadata 改变时使用 `skill-creator/scripts/generate_openai_yaml.py` 重新生成。
4. 从当前正式档案生成给人阅读的 HTML：

   ```powershell
   node scripts/render-language-style-html.mjs <目标 Skill 目录>
   ```

   需要立即交给用户查看时增加 `--open`，让系统浏览器打开页面：

   ```powershell
   node scripts/render-language-style-html.mjs <目标 Skill 目录> --open
   ```

5. 先运行 `skill-creator/scripts/quick_validate.py <目标 Skill 目录>`，检查基础 Skill 结构。
6. 再运行专用校验：

   ```powershell
   node scripts/validate-language-style-skill.mjs <目标 Skill 目录> [--forbid-source <作者、人物或作品名称>]
   ```

专用校验先检查五份档案、规则字段、证据报告、HTML 阅读版及同步指纹、直接链接、长文件索引、metadata、私人路径、来源名称，以及运行时是否混入暂定或否决规则；最终交付时再加 `--require-complete`。完整校验除核对四层状态外，还独立检查每层档案的必需参数、正向单位数、对照证据、可执行来源规则和通过验证的 observation；段落与整篇还必须记录人工复核。随后核对正文文风记录、目标语言、逐文件正文哈希和四层独立复核。报告自称 `complete`、正文只在表格里描述文风，或修改正文后仍沿用旧复核记录时都必须失败。结构通过但成熟度为 `partial` 或 `insufficient` 的结果只能作为未完成提取，不得标为正式完成版。
7. 使用全新子 Agent 或独立任务执行至少一个短答和一个较完整文档的前向测试。只传目标 Skill 路径和原始用户任务，不传预期答案、缺陷诊断或拟议修复；把运行 ID、执行方式、任务摘要、结果摘要、内容保持和来源隔离结果写入 `validation.forwardGeneration.evidence.runs`。记录结果后再修改 Skill，重新生成 HTML，并重新执行两种校验和前向测试。

## 验证提取结果

至少完成以下验证：

1. **样本与全文**：固定样本发现的方向在全文中是否仍成立；若改变，说明漂移来自哪里。
2. **保留样本**：未参与规则发现的文本是否仍能被档案解释。
3. **对照区分**：同语言、同文体对照是否也同样具备该特征；若是，它可能只是共有写法。
4. **单变量对照**：只改变一个词、主语、句尾、断句或顺序，检验推定效果是否真的由该变量造成。
5. **完整前向生成**：用相同事实生成短答、段落和较完整文档，检查四层选择是否共同出现，而不是只插入代表词。
6. **内容保持**：事实、责任、数字、代码、安全和审批边界是否完全保留。
7. **来源隔离**：普通输出是否没有作者、人物、作品、世界观、原句和私人路径。

验证失败的规则降为“场景限定”或“暂定”，无法排除题材和单场景影响时标为“否决”。

## 命名语言风格

名称在 `LexicalProfile`、`NonLexicalStyleProfile` 和最终 `StyleProfile` 通过样本外复核后确定。它是对可迁移语言机制的短称，不是来源标签。

- 中文正式名称使用“二至四字核心特征 + 语言风格”。核心特征优先概括推理、节奏、叙事推进、语气控制或词汇选择，例如“理性推演语言风格”“危机推进语言风格”。
- 英文正式名称使用简短特征短语加 `Language Style`，通常控制在一至四个实义词。
- 名称不得包含作者、人物、作品、文件名、站点名、粉丝称呼或其他来源身份。来源只写入溯源记录和证据说明。
- 不用“高级、独特、强烈、冷酷”等缺少判断对象的形容词命名。名称必须能对应档案中已统计、可复核的选择。
- 对白、叙事、说明文或其他文体若形成不同词汇与声音指纹，应分别命名。只有样本外测试证明它们共享主要选择时，才建立总称。
- 名称不是永久标识。新语料改变结论时可以改名；全局或跨任务绑定只引用稳定的“当前语言风格”入口，由它映射到现行 Skill 或档案。更换风格时只修改映射，不修改每一处全局提示词。

若产物是 Skill，还要同步迁移它的对外身份：

- 正文标题和界面 `display_name` 使用目标语言正式名称；Skill 目录 slug 与 frontmatter `name` 使用与该正式名称对应、来源中立的 ASCII kebab-case。例如“理性推演语言风格”可映射为 `rational-inference-language-style`；
- frontmatter `description` 与触发说明只写可观察的词汇、句法、节奏、篇章和适用任务，例如“在需要条件分析、概率判断和明确行动结论时使用”；
- 不写“模仿某人”“某作品风格”或把来源名称当关键词；
- 作者、人物、作品和原始文件名只写入独立的 `source-provenance` 一类溯源文档。普通调用不加载该文档，只有复核来源、更新档案或查询证据时才读取。

## 绑定到 Codex 输出

当用户要求某种文风或提供样本时，按以下顺序执行：

1. 先提取内容卡和段落地图；
2. 从同类样本生成 `LexicalProfile`；
3. 生成 `NonLexicalStyleProfile`，分别提取句式、段落、整篇编排以及横跨其中的声音和表现策略；
4. 保存完整 `StyleExtractionReport`，分开观察、阅读效果、稳定组合和场景适用性；
5. 完成样本、全文、保留样本、对照、单变量和前向生成验证；
6. 再生成最终 `StyleProfile`；
7. 若交付物是 Skill，使用初始化封装建立正式目录，把观察与七项验证写入 `style-extraction-report.json`，填写五份正式档案，并从这些文件生成 `style-guide.html` 阅读版；
8. 使 `SKILL.md`、references 和面向人的 metadata 直接采用目标语言与文风；仅技能名、YAML 键、路径、命令、规则 ID、代码和其他机器合同保持规定格式；
9. 运行系统基础校验与专用语言风格校验，再用全新子 Agent 分别完成短答和长文前向测试；
10. 验证通过后，将这些档案绑定到 Agent 的用户可见自然语言输出；
11. **词汇输出优先**：按照档案选择人称、疑问方式、确定程度、核心词、常用动词、搭配、句首句末习惯、语域和禁用词；不把词频变成机械配额；
12. **四层修改随后**：分别检查词汇、句式、段落和整篇编排；没有稳定证据的层级使用明确标记的任务适配器，不能把候选写法冒充来源风格；
13. 先按内容卡写底稿，再应用上述约束；回读检查内容、事实、责任主体和限制是否保持不变，且来源词与声音指纹是否真正进入输出；
14. 用目标语言和目标文风重新写出内容卡、段落地图、`LexicalProfile`、`NonLexicalStyleProfile`、`StyleExtractionReport`、`StyleProfile`、分析文档和参考文档；这些提取件本身也必须体现所提取的选择。

总体优先级固定为：用户任务与事实边界 > 内容结构 > 风格。风格内部优先级固定为：`LexicalProfile` > 句式、段落和整篇编排的稳定关系 > 声音与节奏 > 修辞和排版。词汇与文风绑定不得改变代码、命令、文件名、标识符、日志、引文原意或安全说明。默认绑定覆盖当前交付及其附带的提取文档或生成 Skill；只有用户明确要求延续时，才将同一档案用于后续无关任务的用户可见输出。
