# 编程设计巡检

## 选择范围与输出

本 Skill 是已有逻辑的分析与巡检入口；[编程设计风格](../programming-design-style/SKILL.md) 是写逻辑前的设计与实现入口。任务同时包含检查和修改时，先判断已有逻辑，再在动手前应用设计规范；不把只读分析自动变成修改。

| 用户要求 | 工作方式 |
| --- | --- |
| 分析、梳理或理解已有逻辑 | 按问题解释实际调用链与数据来源，不强制找缺陷或生成报告 |
| 命名、格式、可读性、错误处理、日志、异步、查找性能、绑定生命周期或测试检查 | 代码规范审计；默认对话输出问题和证据 |
| 职责、状态来源、配置扩展、重复逻辑、模块分工或架构检查 | 设计巡检；追踪相关链路，复杂关系按需配图 |
| 重点检查、详细审查，或重要既有逻辑的高影响疑点 | 按下方详细模式，逐问题取证、复核与形成方案 |
| 可视化设计报告或完整图解 | 使用 [可视化报告](references/visual-design-report.md) |
| 开始编写新逻辑或修改已有实现 | 在动手前转用设计 Skill，遵循授权范围，不强制先做完整巡检报告 |

两类问题可以混合，但不把简单函数审查扩成全仓架构报告。不凑问题数量，不自动建立文件、Hook 或平台；审查请求本身不授权改代码。

## 详细模式

用户要求“重点检查、详细审查、查清来龙去脉”，或本轮发现重要既有逻辑的疑点，可能影响正式数据、存档兼容、资产/奖励、权限、共享接口或多模块行为时，读取 [详细审查与历史取证](references/detailed-review.md)。主动启用时简短说明对象和具体影响依据，不能只因代码旧、模块大或个人不熟悉就升级。

先形成有位置和触发条件的候选问题，再为每个仍可能需要修复的问题安排独立子 Agent 审查；确认相关来源及历史后形成具体到代码、函数、配置和资源的方案。普通命名、格式或低影响局部检查沿用常规流程。

详细模式增加调查深度，不改变原任务权限。已授权修复时，完成必要取证和方案复核后继续实施；仅要求审查或方案时保持只读。

## 规则只有一个来源

先读取 [编程设计风格](../programming-design-style/SKILL.md)，按其条件表加载适用参考；同一版本已读内容复用。本 Skill 不另维护一份设计规则。源文件缺失时说明哪些规范未能核对，仍可按项目明确规则检查，但不能宣称完成用户风格审查。

## 审查顺序

1. **确定目标**：使用用户给定的文件、模块、功能或差异范围；检查相关项目说明和已有改动。单文件审查不强制要求 Git 比较基线。范围不明时从项目入口选择一个能说明理由的小范围，不默认全仓扫描。
2. **寻找证据**：先定位定义、调用者、数据拥有者、配置/持久化入口和现有检查工具，再判断。涉及表现入口时沿真实链路查到业务模块和数据源，不能只读当前 UI。旧文档与实际调用冲突时用代码、配置和历史核对。
3. **核对适用规则**：按下表寻找证据，具体要求使用设计 Skill 的对应参考。不因某个词出现就认定问题；没有证据的推断列为待确认。
4. **验证并报告**：运行与目标匹配且不超出授权的最小检查；先确认命令是否会写文件，纯审查使用检查模式。按行为风险排序，说明位置、原因、最小改法、验证结果及未覆盖范围。

| 触及问题 | 应定位的证据 |
| --- | --- |
| 业务状态、内容和流程扩展 | 定义数据、作用域、加载入口、执行能力；新增同类内容是否还要改业务代码 |
| 前后端或多入口数据不一致 | 命令是否到达拥有者、实际写入与独立读取结果、展示来源与刷新责任 |
| 逻辑/表现职责或重复规则 | 正式状态与规则的定义、调用链、其他表现入口、现有可复用模块 |
| 身份、配置与缓存 | 稳定标识生成、引用关系、源数据与派生数据、失效与重建入口 |
| 存储与同步框架复用 | 项目专项规范、真实记录类型与调用链、业务值和存储值转换、查询的隐式写入、对象生命周期、保存结果与原子范围、诊断元数据来源；调用了底层框架不等于上层没有重复实现 |
| 运行时对象查找 | 对象稳定 ID、拥有者索引及增删更新入口；热路径是否反复遍历、按名字找对象或调用运行时 `Find` |
| 海量数据展示 | 当前量级与增长、首屏查询、稳定分页/时间分段、摘要与详情边界、虚拟化、缓存上限和失效、取消与乱序结果 |
| 事件绑定与释放 | 固定关系是否可由 Prefab/配置声明、action ID 与处理器注册表、绑定拥有者和有效期、重复绑定、对象池复用、卸载与迟到回调 |
| 新旧逻辑切换 | 兼容调用、当前待删内容与历史、未提交 diff、关联入口及构建/资源清单 |
| 日志与排障 | 统一入口、日志组开关、真实数据源、关联标识、调用链和关键调用堆栈 |
| 多来源锁定 | 锁组、ownerKey、逐次句柄、目标范围内全部获取/释放点及重复/迟到释放路径 |
| 操作阻塞、后台处理与等待恢复 | 按设计 Skill 加载流畅交互规范；定位真实结果依赖、无关操作可用性、主线程耗时、未知结果恢复及等待出口 |
| 代码规范 | 项目规则、实际代码与调用点、成功失败契约、检查命令及结果 |

## 集合数据的局部失败审查

只要涉及集合数据的查询、转换、关联补全、刷新、展示或批量操作，都必须检查本节；不以用户另行提醒为前提。工程判定复用 [最小范围失败与验证要求](../programming-design-style/references/code-quality-standards.md#新增逻辑与校验边界)。

1. 沿实际调用链区分单项坏数据、关联对象缺失、某项请求失败与整次查询/鉴权失败。检查解析、映射、关联查询、并行汇总、分页和批量循环是否因单项异常中断其余有效数据。
2. 在正确性允许时跳过、隐藏或局部标记异常项，让正常数据继续刷新、展示和操作。视频或用户信息异常不能拖垮其他视频的播放和留言；异常邮件不展示也不能阻断正常邮件加载和领取；排名关联对象缺失可隐藏该行或显示“无法加载”，不能使整榜不可用。隔离坏项后仍按真实游标/分页契约继续，不能把过滤后的空页当作没有后续数据。
3. 检查刷新失败是否错误清空有效展示，单项失败是否错误回滚其他已确认成功的独立操作，以及部分失败是否被报告成全部成功。保留定位与恢复依据，按实际需要使用局部提示或有界恢复，不为展示伪造业务身份、奖励、余额或完整性结论。涉及鉴权、关键数据和原子事务时停止受影响的操作，让无依赖的功能继续；不能用全局吞错维持表面可用。
4. 对审查建议本身执行同样检查：说明修改后故障影响范围与正常数据可用性；只建议改成抛异常、加校验或拒绝整批，不能算完成方案。依据现有入口验证一个坏项夹在正常项中、批量中途失败、刷新整次失败及相关分页边界；静态取证与实际运行分别报告，未执行的验证明确列为缺口。

## 结论格式

- **设计矛盾**：职责、数据归属、依赖或协作方式有问题。
- **代码规范问题**：命名、结构、控制流、错误处理、注释、日志、格式或测试有可定位问题。
- 每项给出文件与准确行号、违反的适用规则、触发条件/后果、最小改法和验证证据。设计类附必要的调用/数据关系；不以抽象架构术语替代具体问题。
- 区分已观察事实、推断和待确认项；没有行级证据不写成确定缺陷。证据可以支持多个问题，但不要反复粘贴同一规则。
- 没有发现时说明检查范围及验证状态，不制造候选。用户已给方向时继续该方向，不固定追加“先深入哪个”的问题。
- 未决取舍确实影响职责、数据归属、兼容性或成本时，再按设计 Skill 比较方案；不把评审意见自动扩成实施计划。
