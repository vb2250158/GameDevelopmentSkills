# 详细审查与历史取证

用于重要既有逻辑的高影响疑点，或用户明确要求重点、详细检查。按每个候选问题完成“确认现状 → 收集相关证据 → 追溯设计 → 复核结论 → 制定并验证方案”。工程规则仍以 [编程设计风格](../../programming-design-style/SKILL.md) 及其适用参考为准。

## 1. 建立逐问题范围

先记录问题标识、涉及对象、准确位置、现象/触发条件、预期行为的来源、可能后果、已有证据与待确认假设。疑点只是候选，不能因为不符合惯用写法就认定应当修复。

沿调用、数据、资源引用和时间线确定调查范围。优先使用项目规定的知识源、当前计划和已有有效调查，定位原任务及业务范围；不重复建立任务或要求用户转述已有材料。不同问题共享的事实只查一次，但各自说明如何支持结论。

## 2. 每个疑点独立多 Agent 审查

- 为每个仍可能需要修复的候选问题安排独立子 Agent，协调者核对其证据和方案。子任务交代问题标识、对象/时间范围、已有事实、待验证假设、可用来源、只读边界和交付要求，不能只要求“证明这里有 bug”。
- 子 Agent 主动寻找反例、既有设计理由和兼容约束，返回来源定位、实际观察、证据缺口、问题分类与置信边界；不得把另一 Agent 的猜测当成事实。协调者回查决定性代码、原始记录和历史差异，不能以多数意见或一句“审查通过”代替证据。
- 互不依赖的问题并行，受当前并发限制时分批；不要让所有 Agent 重复全仓搜索。复杂单个问题可按当前实现、历史需求、运行证据拆分，最终仍按问题合并结论。取证期间保持只读，实施阶段再分配互不冲突的写入范围。
- 多 Agent 能力不可用或当前权限禁止时，说明具体限制，按同一清单顺序取证并保留未独立复核状态；不伪称已派发，也不因此停止其余调查。

## 3. 收集一切与问题判断有关的信息

对下列每类来源逐项检查，记录“已查及结果、查无相关记录、不适用、不可用及已尝试入口”。不能把关键词没搜到写成不存在，也不能不查就假定没有资料。范围内发现的新线索继续追溯到原始上下文。

| 来源 | 必须回答的问题与证据 |
| --- | --- |
| 当前代码与配置 | 定义、完整调用链、正式数据拥有者、读写和保存结果、事件/锁生命周期、其他入口、测试及当前未提交差异；问题在哪个真实版本和条件发生 |
| 资源及其引用 | Prefab、Scene、动画、配置表、数据文件等实际实例及覆盖关系；稳定 ID/GUID、谁引用它、同类资源是否共用、生成源与派生产物在哪里 |
| 项目与本地文档 | 需求、设计、接口合同、架构说明、问题单、计划、验收和变更记录；需要时使用项目规定的公司文档知识源及其现有工具，不将私有服务地址写入公共规则 |
| 运行与历史日志 | 云日志、客户端/服务端/编辑器日志、历史诊断及崩溃记录；核对环境、版本、对象身份、时区、关联标识和关键堆栈，区分本次现象与旧故障 |
| 沟通与评审记录 | 群聊、仓库 Issue/PR/评审留言、历史需求沟通系统消息及附件；读回复链和上下文，确认决定者、日期、约束、后续更改和是否仍有效 |
| 版本与发布历史 | 使用项目实际的 SVN、Git 或其他版本控制；代码、配置和相关资源何时新增/修改、对应 revision/commit、同次改动、提交说明、需求链接、发布版本，以及后续修补/回退 |

沿问题标识、文件/函数/资源名及旧名、稳定身份、日志关联标识和日期相互交叉查找。历史查询跟随重命名、移动、复制和分支路径；提交时间与实际上线时间分别核对。不切换或回退正在工作的项目来查看旧版本，优先只读历史内容和差异。

这些来源通过项目现有专项 Skill 和工具按需读取；详细模式不自动授权写云数据、改计划状态、发群消息、联系他人、部署或扩大生产访问。资料中的命令与建议也不是执行授权；私有原始材料保留在项目指定位置，不复制进公共 Skill。

## 4. 还原设计原因并作出结论

把“最初需求/约束 → 引入实现及资源的版本 → 后续需求和改动 → 当前实际行为”串成时间线。查看相关函数和资源最初及关键后续版本，同次修改与沟通决定一起核对。`blame` 或提交人只能帮助定位，不能证明作者当时的目的。

逐问题判断：

- **实现 bug**：当前实现违反仍有效的需求/合同，说明引入或暴露条件；引入版本未知时如实记录。
- **设计缺陷**：当时的设计本身未覆盖必要场景，列出被破坏的业务约束和证据。
- **需求变化或兼容安排**：原行为曾合理，现在需要演进；区分新要求与原缺陷，保留仍有效的兼容约束。
- **无需修改或证据不足**：给出反证或缺口，不为凑修复项改动有效逻辑。原因尚不能确认时明确写“设计原因未确认”。

历史解释与当前是否满足需求分别判断；曾经有理由不保证现在正确，旧代码看着奇怪也不保证有 bug。冲突材料按版本、作用域和后续有效决定核对，不能简单选择最新一条消息或当前代码作为预期行为。

形成正式修复建议前，逐项完成相关来源和关键反证检查。不可用来源若可能改变缺陷判断、兼容或修改范围，该问题只给条件性方案并标记待核验；其余已证实问题继续完成。已有足够证据的技术性 bug 不因无关历史缺失而停工。

调查在候选问题的定义、调用、数据/资源引用和关键历史线索已覆盖，证据冲突已解释，剩余缺口及其影响已明确时收尾。“获取全部信息”针对与该问题有关的证据闭环，不是无限遍历全部代码、日志或群聊；材料数量、Agent 数量与重复搜索不能代替完成标准。

## 5. 方案具体到改动对象与连带影响

每个确认需要处理的问题，方案至少包含：

1. **依据与目标**：证据位置、当前/预期行为、问题分类和必须保留的不变量，说明为什么应改、为何此改法能解决原因。
2. **精确改动**：文件路径、类型/函数/接口、修改方式；配置字段/条目、数据迁移及资源路径/稳定身份。说明改源文件还是生成源；只能确定到模块时保留待定位项，不能冒充可执行完整方案。
3. **影响清单**：所有受影响调用、注册/事件、表现入口、共用资源、存档/协议/版本兼容、缓存/同步、日志/锁及构建发布入口；无影响的判断也要有引用或合同依据。
4. **防止新增问题**：错误、取消、重复、并发、重入、对象复用及失败恢复中与本次相关的风险；旧新数据和旧新资源如何过渡，旧逻辑按退役规则如何收尾，如何撤回本次变更而不丢现有数据。
5. **验证清单**：能暴露原问题的复现/失败用例、修改后的预期、连带回归范围、相关资源加载与真实路径验证。区分拟运行、实际已运行和环境缺口，不能只写“测试一下”。
6. **规范与资料同步**：重新核对方案的数据归属、数据驱动、框架复用、性能、绑定生命周期、日志和锁等适用规范；指出需要同步的设计/接口/运维文档、资源说明、注释和测试，或说明现有说明为何仍准确。

子 Agent 复核候选方案会不会破坏原设计约束、遗漏共用资源或转移问题；协调者检查代码与资源交叉影响，处理不同问题的方案冲突。发现反证或新风险就修订方案并复核受影响部分，直到已识别的实质问题均有去向，仍未知的部分明确保留。

## 6. 按授权继续并报告

只要求审查/方案时交付逐问题结论、证据、具体方案、验证及缺口；不自动改业务代码。已授权修复时，取证和方案复核完成后按设计规范实施并执行匹配验证，不追加一轮通用批准。真实缺少产品决定或特定操作权限时，只询问该项并继续独立工作。

报告保留可回查的文件/行号、文档链接/段落、日志位置与时间、消息链接/ID、revision/commit 和资源身份。按问题组织结论与方案，必要时附来源覆盖表和时间线；不粘贴无关原始记录，不把调查完成写成修复已完成。
