# 长文和文档

## 面向读者组织

先确定唯一主要读者，以及读者看完后要完成的动作或判断。按读者任务组织内容，不按作者调查顺序堆材料。

先删掉与该动作或判断无关的内容，再决定文档结构。不要为了保留原文信息量而保留编写过程、材料来源、档案关系或重复限定。

每段承担一个明确作用，并提供前文没有的新信息。删除只重复标题、总结上一段或用另一种说法重述同一事实的段落。

维护记录和执行说明中，责任主体已由上下文确定时省略第一人称。责任归属会影响判断时保留具体主体。

常见顺序：

1. 当前结果或问题；
2. 事实与范围；
3. 判断及依据；
4. 待补充的信息或失败方式；
5. 下一步、责任主体和成功标准。

只有并列证据较多时才显式使用“已确认 / 未确认 / 下一步”等小节。短文不强行套结构。

## 技术说明

- 先写外部行为，再写内部机制。
- 内部模块名第一次出现时说明它对用户或维护者意味着什么。
- 用代码、配置、日志或测试说明范围，不用“体系化、全链路、深层次”等词扩大成果。
- 测试结果只覆盖实际运行的测试，不从单元测试推到完整运行时结论。
- 文件开头的说明只写文件用途、当前版本、关键参数和必要限制。维护过程和数据整理方式放到维护文档，不写进普通说明。

## 方案和调查

- 方案比较必须有相同目标和具体维度，例如改动范围、兼容性、恢复成本、验证条件。
- 调查结论说明证据支持的结果和待补充的信息。用户询问排除项时，再说明排除了什么。
- 发现原判断错误时直接修正，不用大段“不是……而是……”制造戏剧性。

## 用户文档

先说明用户能做什么、要做什么、怎样知道成功、失败后怎么办。架构术语只在会影响选择或排障时出现。

## 删除检查

完成初稿后，逐段删除：

- 只是在宣布“我要开始解释”的句子；
- 没有证据的悬念；
- 没有具体对象的共情和升华；
- 重复同一判断的纠偏句；
- 没有增加范围、因果或行动信息的抽象词；
- 与读者任务无关的作者备注和写作过程。
