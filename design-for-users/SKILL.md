# 面向用户设计

从用户要完成的事组织内容。需求是约束，写进产品前转化为用户能理解的事实与动作。

## 明确读者与结果

每页或每段选定主要读者：普通使用者、操作维护者、集成者或开发者。公共文档也可能面向开发者；保留该读者需要的精确术语。

写前确定：为什么来到这里、希望得到什么、现在做什么、看到什么算成功、失败后如何继续。优先由当前产品和证据补齐，确有业务选择时再询问。

## 界面与文案

- 每屏有清楚的主要任务和下一步。用用户认识的对象与动作命名导航、字段和按钮，避免照搬模块或数据库字段。
- 状态写清发生了什么及可做什么。覆盖实际会出现的加载、空、部分成功、失败、禁用与恢复；不把正常状态枚举写成永不扩展的业务规则。
- 默认收起日志、原始配置与技术标识；用户决策、排障或风险需要时在对应位置解释。不能把必要错误隐藏成空结果。
- 使用自然、完整的句子；术语首次解释普通含义，代码/API 合同保留原名。对“更稳、更强、更安全”等评价写明具体结果。
- 项目既有设计系统和组件继续复用。字体、颜色、布局及平台实现由对应技能处理。
- 用户操作失败后保留已输入内容和导航位置，提供一项明确的主要恢复动作。

## 文档

README 先说明帮助完成什么，给最短有效操作、成功证据和主要限制，再链接细节。使用指南按任务和决定组织；维护指南写前提、命令、症状与恢复。索引按读者和使用时机分组。

提示词、验收措辞、TODO、截图占位、制作说明和“本轮新增”等过程信息留在计划或维护记录。确实影响用户选择的限制，改写为产品事实。

## 交付前检查

第一次接触的读者能否理解用途、点击结果及下一步；是否混入内部模型和制作过程；成功、失败、限制和恢复是否可观察。评审引用具体文案或控件，说明后果并给替换方案，不只列原则。
